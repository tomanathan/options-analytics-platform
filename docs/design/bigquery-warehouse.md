# BigQuery as the warehouse for silver and gold

Status: specification for the `feat/bigquery` branch. Written against `main` at `c085db9`.

## Decision in one paragraph

Silver and gold move to BigQuery: the dbt SQL models build there, from bronze tables loaded out of the Iceberg catalog. The analytics stay on DuckDB: the seven dbt Python models keep running in process on a local DuckDB file whose `gold` schema is pulled from BigQuery, and the explorer API, the report and the scripts keep reading that file. Snowflake, the paper production target that was never provisioned, is removed. DuckDB also stays as the offline target for `make check` and CI, which build the whole project on the synthetic bronze catalog with no credentials. This is a common split (a cloud warehouse for the SQL layers, a local engine for Python analytics) and the docs say so plainly.

## The sandbox constraints, which shape the design

The project runs in the BigQuery sandbox (no billing account, no card). The sandbox page states three limits that matter:

1. "You are granted a lifetime limit of 10 GiB of storage. This quota is not refunded upon data deletion." Storage is cumulative over the project's life, so every byte ever written counts, including rewrites.
2. "All tables, views, and partitions automatically expire after 60 days."
3. DML statements (MERGE, DELETE, UPDATE), streaming inserts and the Data Transfer Service are unavailable. Load jobs, copy jobs, query jobs and DDL (`create or replace table ... as select`) are available. Query compute is the free tier's 1 TiB a month.

Consequences, each implemented below:

- **Nothing is rewritten nightly.** Bronze loads only the partitions the refresh touched; `fct_option_quote` writes only new partitions; the small marts are views on BigQuery so they hold no storage. The nightly write volume is a few megabytes.
- **Everything is rewritten once a month**, on the first run of the month, so no partition reaches its 60-day expiry: bronze is fully reloaded and dbt runs with `--full-refresh`. That costs about 0.2 GiB a month at today's volume (1.8 million chain rows, 18 thousand price rows), so the lifetime cap lasts about three years. The runbook states this budget, the `bq-usage` target measures it, and the first step of the runbook's "upgrade" section is enabling billing, which removes both the cap and the expiry while staying inside the free tier at this volume.
- **Incremental models cannot use MERGE.** `fct_option_quote` uses dbt-bigquery's `insert_overwrite` strategy with `copy_partitions: true`, which replaces partitions through copy jobs instead of DML. The implementer verifies on the real project that this runs in the sandbox; if it does not, the fallback is `partitions` set statically to the new trade dates (still copy jobs). DuckDB keeps `delete+insert`.

## Layout of the change

### Dependencies

`pyproject.toml`: remove `dbt-snowflake`; add `dbt-bigquery>=1.10,<2` and `google-cloud-bigquery>=3.25,<4` to the main dependencies (`db-dtypes` comes with it; no `google-cloud-bigquery-storage`, the REST path is free and the pulls are small). `uv lock`, `make lock-export`, `make lock-check` clean; `docker/requirements-dbt.txt` regenerated by the same target. ADR 0006 says the image installs from the lock, so the Airflow image gains `dbt-bigquery` as a side effect, which is fine and noted.

### dbt

- `dbt/profiles.yml`: replace the `prod` Snowflake output with

  ```yaml
  bigquery:
    type: bigquery
    method: oauth                       # Application Default Credentials: gcloud locally, Workload Identity in CI
    project: "{{ env_var('OAP_BQ_PROJECT') }}"
    dataset: "{{ env_var('OAP_BQ_DATASET', 'oap') }}"   # custom schemas land in `silver` and `gold`
    location: "{{ env_var('OAP_BQ_LOCATION', 'US') }}"
    threads: 4
    priority: interactive
    job_execution_timeout_seconds: 600
    job_retries: 1
  ```

  `DBT_TARGET` selects `dev` (DuckDB, default) or `bigquery`.
- `dbt/models/staging/sources.yml`: the `bronze` source is `target.database` / `bronze` on every target; the Snowflake environment variables go.
- `dbt/macros/register_bronze.sql`: the header comment describes BigQuery instead of Snowflake (the default dispatch is already a no-op there). Add mode `none` to `OAP_DBT_SOURCE` on DuckDB: the hook does nothing, for a DuckDB file whose gold comes from BigQuery rather than from local bronze. The mode guard that refuses to mix synthetic and iceberg builds in one file treats `none` as compatible with `iceberg` (the gold rows are the same data), and refuses `synthetic`.
- `dbt/dbt_project.yml`: the marts get `+materialized: "{{ 'view' if target.type == 'bigquery' else 'table' }}"` except `fct_option_quote`, whose config becomes

  ```sql
  {{ config(
      materialized='incremental',
      incremental_strategy=('insert_overwrite' if target.type == 'bigquery' else 'delete+insert'),
      unique_key='trade_date',
      partition_by={'field': 'trade_date', 'data_type': 'date'} if target.type == 'bigquery' else none,
      cluster_by=['underlying'] if target.type == 'bigquery' else none,
      copy_partitions=(target.type == 'bigquery'),
      on_schema_change='fail',
  ) }}
  ```

  The analytics models stay `enabled: target.type == 'duckdb'`.
- Portability audit of every SQL model, macro, singular test and schema test against GoogleSQL: `cast(... as varchar)` becomes `{{ dbt.type_string() }}`, string concatenation uses `{{ dbt.concat([...]) }}` or `||` (valid in both), `qualify` is valid in both, `greatest` is valid in both, `dbt_utils.generate_surrogate_key` is cross-database, `dbt.datediff` is cross-database. The seed `watchlist` column types use `string` on BigQuery: set `+column_types` per target with `{{ dbt.type_string() }}`. The implementer runs the full `dbt build --target bigquery` on the real project to find the rest.
- `tests/dbt/test_project.py` asserts the targets are `dev` and `bigquery` and the analytics are disabled off DuckDB.

### Scripts (`scripts/`, I/O in `main` and thin client wrappers only; the logic is pure and tested)

- `load_bronze_bigquery.py`: reads each `BRONZE_TABLES` spec from the local Iceberg catalog (`catalog_from_env`, `read_range`) and loads it into `bronze.<table>` with parquet load jobs from memory (`load_table_from_file` with a `BytesIO` parquet buffer; no Cloud Storage). The table is partitioned by day on `trade_date` and clustered by `underlying`. Modes: `--since YYYY-MM-DD` loads one job per trade date from that date on, each with `WRITE_TRUNCATE` on the partition decorator `table$YYYYMMDD` (replacing a partition without DML); `--full` truncates the whole table in one job. Default: `--since` equals the newest `trade_date` already in BigQuery minus 7 days (absence is not deletion, so re-loading a week is harmless and covers a late vendor correction); with no table yet, `--full`. The dataset is created if missing, in `OAP_BQ_LOCATION`. Prints rows and bytes per job. Pure helpers: `plan_loads(local_dates, remote_max, since, full) -> list[date] | "full"`, `job_config(spec, partition)`, `parquet_bytes(frame)`.
- `pull_gold_bigquery.py --db .dbt-local/oap.duckdb`: copies the gold tables from BigQuery into the DuckDB file's `gold` schema. `fct_option_quote` is pulled incrementally: rows with `trade_date` after the local maximum (minus 7 days, same reasoning, with `delete` of those dates first); `--full` replaces it. The four small marts are pulled whole each time. Rows arrive as arrow (`QueryJob.result().to_arrow(create_bqstorage_client=False)`) and are written through DuckDB's arrow registration, so dtypes survive (dates stay dates, decimals become doubles as the DuckDB build does today). After the pull, `bronze.registered_snapshot` in the file records mode `none`, so the next analytics run's hook accepts it. Prints rows per table and the resulting `max(trade_date)`.
- `gcp_github_auth.sh`: idempotent `gcloud` commands that create the service account `oap-nightly`, grant it `roles/bigquery.dataEditor` and `roles/bigquery.jobUser` on the project, create the Workload Identity pool `github` and provider `github-oidc` for `https://token.actions.githubusercontent.com` restricted to `assertion.repository == 'tomanathan/options-analytics-platform'`, bind `roles/iam.workloadIdentityUser` to the repository principal set, and print the three values to put in the repository's **variables** (not secrets): `GCP_PROJECT`, `GCP_WIF_PROVIDER`, `GCP_SA_EMAIL`. No key file is ever created.
- `bq_usage.py`: prints the project's BigQuery storage in use per dataset and the bytes written in the last 30 days from `INFORMATION_SCHEMA.TABLE_STORAGE` and `INFORMATION_SCHEMA.JOBS`, so the lifetime budget can be watched. `make bq-usage`.

### Makefile

`bq-load-bronze [SINCE=YYYY-MM-DD] [FULL=1]`, `dbt-build-bigquery [FULL=1]` (`DBT_TARGET=bigquery dbt build`, `--full-refresh` when `FULL=1`), `bq-pull-gold [FULL=1]`, `analytics-local` (`OAP_DBT_SOURCE=none dbt build --select tag:analytics --target dev` on `.dbt-local/oap.duckdb`), `warehouse` (the four in order), `bq-usage`, `gcp-github-auth`. `dbt-build-local` stays as the offline full build. `BQ_ENV := OAP_BQ_PROJECT=$(OAP_BQ_PROJECT)` read from `.env` (the Makefile already loads `.env` if it does; otherwise document `set -a; . ./.env`).

### Nightly workflow

`.github/workflows/nightly.yml` after the bronze refresh and the cache save:

1. `google-github-actions/auth@v2` with `workload_identity_provider: ${{ vars.GCP_WIF_PROVIDER }}` and `service_account: ${{ vars.GCP_SA_EMAIL }}` (needs `permissions: id-token: write`, which the job gets in addition to `contents: write`).
2. `make bq-load-bronze` with `FULL=1` when it is the month's first run (`date +%d` equals `01`, or the `full_history` input is set), else the default incremental window.
3. `make dbt-build-bigquery` with `FULL=1` under the same condition.
4. Restore `.dbt-local/oap.duckdb` from the Actions cache (key `gold-duckdb-<run id>`, restore-keys `gold-duckdb-`), `make bq-pull-gold` (full when the cache missed), `make analytics-local`, save the cache.
5. `make report`, the `gold-duckdb` and `results` artifacts, the results commit and the step summary as today, with the summary also naming the BigQuery project and whether the run was a full rewrite.

`OAP_BQ_PROJECT: ${{ vars.GCP_PROJECT }}` is set at the job level. When the three variables are unset, the workflow fails at the auth step with a clear message in the summary (a `preflight` step checks them).

## Ownership and verification

One implementer (branch `feat/bigquery`) owns everything above. The GCP project and Application Default Credentials come from the user; the implementer checks for `~/.config/gcloud/application_default_credentials.json` and `OAP_BQ_PROJECT` in `.env` before the live phase. Offline work first (dependencies, dbt changes, scripts, tests, docs, `make check` green), then the live phase on the real project: `make bq-load-bronze FULL=1`, `make dbt-build-bigquery FULL=1` (all tests pass on BigQuery), `make bq-pull-gold FULL=1` into a scratch DuckDB path (never into `.dbt-local/oap.duckdb` while the explorer serves it), `make analytics-local` on that file, `make bq-usage`, and `scripts/gcp_github_auth.sh`. The report lists bytes written, the time of each step and the three repository variables. If credentials are absent when the offline work is done, hand back with the live phase marked pending.

The integrator merges, sets the repository variables, triggers the nightly workflow, pulls the artifact, and verifies the explorer still serves the same gold.
